## 1. 整体方案

本仓库采用**轻量级、基于环境变量 + 本地 .env 文件**的配置体系，没有引入统一的配置中心或 YAML/TOML 配置框架。配置按运行时代码分层加载：

- **后端（Express）**：通过 `process.env` 读取 `PORT`、`NODE_ENV`，由启动脚本注入。
- **前端（PC 管理后台）**：通过 Vite 的 `import.meta.env.VITE_*` 注入构建期常量，使用 `.env` / `.env.production` 区分环境。
- **小程序端**：通过 Vite dev server 的 `proxy` 将 `/api` 转发到后端，不直接读外部配置。
- **Harness 层**：用 `harness/config/environment.json` 声明运行时、数据库、服务端口、测试环境变量及功能场景，配合 `harness/scripts/*.sh` 统一启动/停止。

## 2. 关键文件与位置

| 层级 | 文件 | 作用 |
|---|---|---|
| 后端入口 | `star-park/server/src/index.js` | 读取 `process.env.PORT`（默认 3001），启动 Express |
| 后端应用 | `star-park/server/src/app.js` | 注册路由与健康检查，无外部配置依赖 |
| 数据库初始化 | `star-park/server/src/database.js` | 根据 `process.env.NODE_ENV === 'test'` 选择内存库 vs 文件库；WAL 模式 + 外键开启 |

| PC 前端 .env | `star-park/pc-admin/.env`、`.env.production` | 定义 `VITE_QODERWAKE_INVOKE_URL`、`VITE_QODERWAKE_GOAL_ASSOC_URL`、`VITE_QODERWAKE_PAT` |
| PC 前端代理 | `star-park/pc-admin/vite.config.js` | 开发时 `/api` → `localhost:3001`，`/qoderwake-api` → `https://api.qoder.com` |
| 小程序代理 | `star-park/miniprogram/vite.config.js` | 开发时 `/api` → `localhost:3001` |
| Harness 环境声明 | `harness/config/environment.json` | 声明语言版本、数据库路径、服务端口、测试 `NODE_ENV=test`、`PORT=3002` 等 |

## 3. 架构与约定

### 3.1 后端配置
- 仅依赖两个环境变量：`PORT`（默认 3001）和 `NODE_ENV`。
- `NODE_ENV=test` 时 `database.js` 使用 `:memory:` SQLite，否则在 `star-park/server/data/star-park.db` 持久化。
- 数据库通过内联 SQL 建表 + 可重复执行的 `ALTER TABLE ... ADD COLUMN` 做轻量迁移，不存在独立迁移脚本。
- 无配置文件（YAML/JSON），所有运行时参数来自环境变量。

### 3.2 前端（PC 管理后台）配置
- 使用 Vite 的 `import.meta.env.*` 注入**构建期常量**，变量必须以 `VITE_` 前缀开头。
- 通过 `.env`（开发）和 `.env.production`（生产）分别提供不同的 QoderWake 调用地址与 PAT。
- 开发时通过 `vite.config.js` 的 `proxy` 把 `/api` 转发到本地 3001 端口，把 `/qoderwake-api` 重写为 `https://api.qoder.com/v1/qoderwake`。
- 若 `.env` 缺失对应变量，API 调用会抛出明确错误（如 `QoderWake 配置缺失，请检查 .env 文件`）。

### 3.3 小程序端配置
- 通过 `vite.config.js` 的 dev proxy 将 `/api` 指向 `http://localhost:3001`，无需额外 `.env`。

### 3.4 Harness 环境编排
- `environment.json` 集中描述：运行时语言/版本、数据库类型与路径、服务端口、测试环境变量、功能场景步骤、以及 `setup/start/teardown` 脚本路径。
- `start-server.sh` 通过 `export PORT="${PORT:-3001}"`、`export NODE_ENV="${NODE_ENV:-development}"` 注入环境变量后启动后端，并用 `curl http://localhost:${PORT}/api/health` 轮询确认就绪。
- 测试环境通过 `environment.json` 的 `test_environment.env_vars` 指定 `NODE_ENV=test`、`PORT=3002`，使测试走内存数据库且不与开发端口冲突。

## 4. 约定与约束

- **环境变量命名约定**：后端使用 Node 标准 `process.env` 变量名（`PORT`、`NODE_ENV`）；前端必须使用 `VITE_` 前缀的变量才能被 Vite 注入。
- **敏感信息隔离**：QoderWake 的 URL 与 PAT 放在 `.env` 中，不在代码里硬编码；生产与开发通过不同 `.env` 文件切换。
- **测试与生产行为分离**：`NODE_ENV=test` 是触发内存数据库的唯一开关，禁止在生产环境使用该值。
- **数据库路径固定**：SQLite 数据文件始终位于 `star-park/server/data/star-park.db`，由 `database.js` 自动创建目录与文件。
- **服务端口默认值**：后端默认 3001，测试默认 3002；可通过 `PORT` 覆盖。
- **健康检查契约**：`GET /api/health` 返回 `{ status: 'ok', timestamp }`，作为服务就绪判定依据。
- **无全局配置对象**：项目未实现统一的 config loader（如 dotenv 解析、config store），每个模块自行读取所需环境变量，因此新增配置需在各相关文件中同步添加读取逻辑。
