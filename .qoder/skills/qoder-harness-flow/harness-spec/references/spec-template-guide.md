# 规格模板指南

本文件定义 harness-spec 产出的 **三层 artifact 格式**。每个 spec 是 `docs/exec-specs/<slug>/` 目录，包含三个文件。所有 artifact 必须严格遵循此格式。

---

## Spec 目录结构

```
docs/exec-specs/<slug>/
├── spec.md             # 需求定义 + 技术方案 + 依赖图
├── tasks.md            # 任务列表（executor 可机械执行，含 checkbox 进度追踪）
└── acceptance.md       # 验收标准（executor 可机械验证，SHALL 约束 + MANDATORY 全局验证）
```

---

## 1. spec.md

```markdown
# [任务标题]

## 需求背景

[为什么要做这个变更？当前问题是什么？业务影响是什么？]

## 目标

[期望达成的结果，具体可衡量]
- 目标 1: [描述]
- 目标 2: [描述]

## 范围

### 包含
- [明确在范围内的内容]

### 排除
- [明确不在范围内的内容]

## 约束与设计原则

- [约束 1: 例如"不修改 API 契约"]
- [约束 2: 例如"保持向后兼容"]

## 风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| [风险描述] | [影响范围] | [具体措施] |

## 技术方案

[概述实现方案的核心思路、关键技术选型、架构决策]

### 执行顺序

[基于依赖关系的建议执行顺序]
1. [步骤 1]（无依赖，先行）
2. [步骤 2]（依赖步骤 1）
3. [步骤 3]（依赖步骤 1, 2）

## 依赖图

### 代码依赖图
| 组件 | 依赖 | 被依赖 |
|------|------|--------|
| [file/module] | [upstream] | [downstream] |

### 影响范围
- **直接修改**: [文件列表]
- **间接影响**: [接口/类型变更波及的文件]
```

### 格式规则

- `## 需求背景` 必须说明 WHY，不是 WHAT
- `## 目标` 必须可衡量（"降至 200ms"，不是"优化性能"）
- `## 范围` 必须同时列出包含和排除
- `## 技术方案` 概述核心实现思路，不需要代码级细节（代码级细节在 tasks.md）
- `## 依赖图` Standard/Complex 任务必须包含，Trivial 任务可写 "单文件修改，无跨组件依赖"
- 不允许出现 `[TODO]` / `[TBD]` / `<placeholder>`

## 2. tasks.md

```markdown
# 任务列表

## Task 1: [任务名称]
- [ ] `full/path/to/file.ext`

[当前代码存在什么问题。为什么要这么改，用自然语言描述。]

```[lang]
[修改后的关键代码片段]
```

## Task 2: [任务名称]
- [ ] `full/path/to/new-file.ext` — (NEW FILE)

[缺少什么功能/文件。为什么要新增这个文件。]

```[lang]
[新文件的关键代码片段]
```

## 涉及文件汇总

| 操作 | 文件 |
|------|------|
| 新建 | `full/path/to/file.ext` |
| 修改 | `full/path/to/file.ext` |
| 移动 | `old/path` → `new/path` |
| 删除 | `full/path/to/file.ext` |
```

### 格式规则

- 每个 Task 以 `## Task N: <name>` 二级标题开头（N 从 1 递增），提供视觉分隔
- 标题下一行用 `- [ ] \`file/path\`` checkbox 标注目标文件
- executor 完成一个 Task 后立即标记 `- [x]`
- 标题和 checkbox 之后用自然语言段落描述问题和原因，不使用 `Problem:`、`Reason:` 等标签
- 有代码变更的 Task 直接放裸代码块（不加 `After`、`Before` 等标签）
- 新建文件：checkbox 行标记 `(NEW FILE)`
- 删除文件：描述段落说明删除原因，不需要代码块
- Task 编号必须与 acceptance.md 一一对应
- `## 涉及文件汇总` 必须覆盖所有 Task 提到的文件

### 禁止模糊描述

以下模式 **禁止出现**：
- "TBD"、"TODO"、"待定"、"后续补充"
- "添加适当的错误处理"（没有具体代码）
- "编写相关测试"（没有具体测试名）
- "类似 Task N"（必须重复写出具体内容）
- "修改 service 层"（没有具体文件路径和函数名）
- "优化性能"（没有具体措施）

## 3. acceptance.md

```markdown
# 验收标准

## Task 1: [任务名称]

### 验证命令
1. `[具体命令]` — 预期输出 SHALL 包含: `[输出]`
2. `[具体命令]` — 预期输出 SHALL 包含: `[输出]`

### 预期行为
- [具体的可观测行为 1] SHALL [预期结果]
- [具体的可观测行为 2] SHALL [预期结果]

### 边界 Case
- [边界场景 1]: SHALL [预期行为]
- [边界场景 2]: SHALL [预期行为]

## Task 2: [任务名称]
...

## 全局验证 (MANDATORY)

> ⛔ executor 在所有 Task 标记 `- [x]` 后 **MUST** 执行本段所有命令。任何命令失败则报告错误并尝试修复，**SHALL NOT** 跳过或声明任务完成。

### 构建验证
`[build command]` — SHALL 输出: BUILD SUCCESS

### 回归验证
`[test command]` — SHALL 输出: 0 failures

### 功能验证场景
1. [场景描述]: [验证步骤] → SHALL [结果]
2. [场景描述]: [验证步骤] → SHALL [结果]
```

### 格式规则

- 每个 Task 以 `## Task N: <name>` 开头，与 tasks.md 编号一一对应
- 所有验证标准 **MUST** 使用 SHALL/MUST 约束语义（RFC 2119），禁止使用 "应该"、"建议" 等弱约束
- **验证命令** 必须是可直接执行的命令 + 预期输出
- **边界 Case** 至少 1 个（Trivial 任务可为 "无需额外边界测试"）
- `## 全局验证 (MANDATORY)` 必须包含构建、回归、功能三类，executor 必须在所有 Task 完成后强制执行
- 验证方式不允许只写 "跑测试" — 必须写具体命令和预期输出

## 自审检查清单

写完三个 artifact 后，逐项检查。任何一项为 NO，回去修改：

### spec.md
- [ ] 需求背景清楚吗？读者能理解 WHY？
- [ ] 目标可衡量吗？
- [ ] 范围边界明确吗（包含 + 排除）？
- [ ] 技术方案概述清晰吗？
- [ ] 依赖图覆盖所有直接影响的文件吗？（Trivial 可简化）

### tasks.md
- [ ] 另一个开发者能不问问题就执行每个 Task 吗？
- [ ] 每个 Task 都有 checkbox（`- [ ]`）吗？
- [ ] 有代码变更的 Task 都有自然语言描述和代码块吗？
- [ ] 涉及文件汇总完整吗？
- [ ] 有 Placeholder 残留吗？搜索 TBD/TODO/待定，必须为 0

### acceptance.md
- [ ] Task 编号与 tasks.md 一一对应吗？
- [ ] 每个 Task 有具体可执行的验证命令吗？
- [ ] 所有验证标准使用 SHALL/MUST 约束语义吗？
- [ ] `## 全局验证 (MANDATORY)` 段落存在吗？
- [ ] 全局验证覆盖构建+回归+功能三类吗？
- [ ] 验证命令有预期输出吗？

### 跨文件一致性
- [ ] tasks.md 的 Task 数量 = acceptance.md 的 Task 数量？
- [ ] 所有文件无 `[TODO]` / `[TBD]` / `<placeholder>` 残留？
